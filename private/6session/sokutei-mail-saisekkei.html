3. 再設計 ── 1本の道にする

決めたこと3つ

(1) メアドの正本は中継（Workers）に置く。UTAGE は「顧客登録の写し」にする。

理由：中継の KV なら何列でも持てて、突き合わせも1か所で済む。

Mits様の「workerはAI-Mitsに帰ってきたときにメールで判定するから必要／UTAGEでは顧客登録だからこれも必要」と一致する。

🔧 UTAGE 側にも UTM を残す（2026-09-11 に引き直して分かったこと）。

message_reader_create に utm_* という名前の引数は無いが、scenario_fields / common_fields は

「キー=項目名、値=文字列」の自由な入れ物で、message_reader_item_create で読者項目を新しく作れる

（reserved_word は freeN が自動採番される）。


シナリオ ★【AI-Mits登録】XU7Gfd7XoiCQ のいまの読者項目 13個（実測）
  name / mail / sei / mei / kana / phone / zipcode / pref / city /
  address / building / event_date / free20(お名前・2026-07-26 に後から作られた)
  → free21 以降が空いている

作る読者項目 5つ（field_group は scenario_fields・data_type は text）

表示名入る値
流入元（utm_source）utage / spro / magmag
流入手段（utm_medium）email
配信名（utm_campaign）20260910_sekidobi など
着地ページchange.7years.life/p/…
初回来訪ISO8601

これで、**form を通った登録は UTAGE の標準 utm_* 5列に、API で作った登録は読者項目5つに**、

どちらでも経路が残る。取りこぼしが出ない。

(2) 登録の窓は「UTAGE の form ＋ 中継」の両方を通す。

理由：UTAGE の登録数・utm_* 5列は form 経由でしか埋まらない。

手本は既に動いている面 ── 8OPXLgTgerHc（機能要望フォーム）の

{"type":"form","scenario_id":"wUS58TtDwzYL","use_reader_item":1,…}。

(3) 測る数字は中継の1か所から出す。台帳はそれを写すだけにする。

理由：いま DL は中継、登録は UTAGE、開封は UTAGE と、3か所に散っていて突き合わせられない。
